# AI 协作全局指引

## 排版

中文排版参照 W3C CLReq 与「中文文案排版指北」，并以以下约定为准：引号使用「」，嵌套引号使用『』；中文与 Latin 字母或阿拉伯数字之间加 1 个半角空格；全角标点前后不加空格；专有名词保持官方拼写与大小写。

## 授权边界

授权只作用于明确的对象和范围。用户已经明确授权，或本指引已经明确预授权的操作，不重复确认，也不得将授权扩展到相邻对象。

## 证据与断言

对「已完成」「已修复」「测试通过」等状态的断言，必须基于本次任务实际获得的现场证据，例如测试输出、diff、日志或现场检查。未验证、无法验证或跳过的部分如实说明。

## 执行过程

<!-- 本节约束内部工作过程；其中产生的工作材料默认不作为用户交付物，除非任务本身要求交付。 -->

### 文件发现

文件发现从已知信息向外扩，不无理由扫描整个文件系统。

候选仓库必须通过 Git 元数据确认，不能仅凭目录名判断；涉及多个 worktree 时，同时确认当前 checkout。

文件名查找优先使用 `fd`，默认遵循 ignore 规则；需要完整盘点时使用 `--hidden --no-ignore`。

### 浏览器自动化

需要操作网页 UI 且 `agent-browser` 可用时，默认使用它：

* 默认启动独立的 headless session，不连接或接管用户当前正在使用的浏览器；`--headed` 仍应启动独立浏览器，不等于连接用户浏览器。
* 需要登录态时，优先使用 `--restore` 或 `--state`；必须复用 Chrome Profile 时使用临时副本或专用 Profile，不直接读写用户正在使用的原始 Profile。认证状态和副本均按 secret 处理，不输出其内容。
* headless 被目标网站拒绝时，改用独立的 `--headed` session；只有用户明确要求控制当前浏览器时，才使用 `--auto-connect`、`--cdp` 或 Chrome connector。
* 为任务创建唯一的 `--session` 并全程复用；按 `open → snapshot -i → 使用 @ref 操作 → 重新 snapshot` 循环执行。页面变化后不得复用旧的 `@ref`。
* 结束时只关闭当前任务的 session，不使用 `close --all`。

### 咨询神谕 CLI

仅在针对性排查仍无法解决问题、存在未决的高影响设计取舍，或需要对大范围修改进行独立复查时，使用：

```bash
amp --mode ultra -x "$(cat /tmp/oracle.md)"
```

本节仅适用于 CLI 咨询，不适用于当前对话的 `oracle` 工具。委托神谕解决一个具体的未决问题，并提供足以判断的最小现场上下文；必要时附当前 Thread ID，供其使用 `read_thread` 核对用户原话。要求神谕只读调查并给出意见，不修改代码。

神谕意见不是现场证据。采纳前先对照当前代码、Git 记录和实测结果核实；实际修改仍由你在当前任务授权范围内完成。不要为了获得一般性确认而调用神谕，也不要重复同一失败尝试。

## 及时小循环：当前对话交付

<!-- 本节产物由用户在当前对话中立即消费；目标是让用户能够马上查看、验证和回应。 -->

### 交付物

除非任务另有指定，需要用户在 Amp 对话或 Web Thread 中查看或下载的最终文件，放入 `.amp/in/artifacts/`，使用 workspace 文件 URI 交付；图片和视频优先内嵌。

需要交付交互式 HTML 时，使用 Bun：

```bash
bun build ./index.html --compile --target=browser --outdir=dist
```

交付一个可通过 `file://` 直接打开的自包含单文件 HTML，并验证页面和交互正常。

`.amp/in/artifacts/` 只存最终交付物；临时文件、日志、缓存和测试产物放在临时目录并及时清理。

没有任务依据时，不创建或修改 `.amp` 下的其他路径。

### 阻塞时通知用户

仅当任务需要用户执行具体操作才能继续，且当前没有其他部分可以推进时，使用 `brrr-now` Skill 发送 `time-sensitive` 通知；对同一阻塞只通知 1 次，其他情况只在当前对话中说明。

从 Amp 发送通知时，使用当前 Amp Thread ID 作为 `thread_id`，使用当前 Amp Thread URL 作为 `open_url`；如果存在更适合接手的真实页面，可使用该页面替代 `open_url`。

### 测试

新增或修改测试时，沿用仓库既有的测试层级，并通过该层级对应的生产入口验证行为。不要 Mock 被测逻辑，也不要在测试中复写生产实现；Mock 只用于隔离当前测试范围之外的协作者或外部边界。

### 临时代码

兼容、迁移、灰度等临时代码必须在行为附近留下符合仓库惯例的 TODO，且注释本身不得依赖当前对话才能理解。

TODO 应说明目标状态、临时代码存在的原因、可验证的删除条件和清理范围；必要时补充无法从邻近代码推知的验证入口或关联清理点。日期只有在到期本身足以决定删除时才作为删除条件。尚未承诺的未来优化或假设接口写普通设计说明，不标 TODO。

### 跟踪与清理

已有 Linear 或 GitHub Issue 承载调查时，在相关代码附近留下 canonical URL。动态讨论、证据和过程记录留在 Issue；代码注释只保留理解当前状态和判断是否需要继续追查所需的信息。

Issue 状态不是删除临时代码的现场证据。清理前必须根据当前代码和现场证据确认删除条件已经成立，并在当前任务范围内完成清理和验证；无法确认或超出范围时保留，并在收尾说明。

除专门的清理任务外，不主动全仓扫描 TODO。自然遇到的相关 TODO 若可能已经过期或与当前代码矛盾，只在与当前任务相关的范围内核验。不要复制或扩散已明确标记为临时的实现模式。

### Git 与 GitHub 身份

Git commit 身份、GitHub 账号和 Git push 凭据彼此独立；不得从一方推导另一方，也不得为了「对齐」而修改另一方。

#### Git commit 身份

每个仓库首次 commit 前，检查实际生效的 Git 用户名、邮箱及其配置来源：

```bash
git config --show-origin --get user.name
git config --show-origin --get user.email
```

已有有效配置且不与仓库的明确要求冲突时直接沿用。不得根据 GitHub 账号、profile 或 noreply 邮箱覆盖，也不得仅为身份对齐写入 repo-local `user.name` 或 `user.email`。

Git commit 身份缺失、与明确要求冲突，且无法从现有上下文唯一确定时，在 commit 前询问。

push 前核对本次新增的 commits：committer 应符合该仓库实际生效的 Git commit 身份；由本次任务创建的 commit，其 author 也应符合预期。保留原作者身份的 cherry-pick、rebase 等情况不得仅因此改写 author。发现异常身份时不得 push。

#### GitHub 账号与 Git push 凭据

本次任务首次向某个 GitHub host 执行外部写入前，用 `gh auth status` 确认当前认证状态和可用账号。

单账号环境直接沿用默认凭据，不提取或注入 token。多账号环境必须先根据目标仓库、组织或用户的明确要求唯一确定本次操作应使用的 GitHub 账号；无法确定时，在外部写入前询问。

不得通过切换全局 active account 完成单次操作，也不得因目标账号权限不足而改用其他账号。需要使用非 active 账号时，凭据只作用于当前命令，不修改持久 Git 或 `gh` 配置。

使用 `gh` 时，例如：

```bash
(
    tok="$(gh auth token --user <login>)" && [ -n "$tok" ] || exit 1
    GH_TOKEN="$tok" gh <command>
)
```

通过 HTTPS 执行 `git push` 时，同样使用命令级凭据，不修改持久 credential 配置：

```bash
(
    tok="$(gh auth token --user <login>)" && [ -n "$tok" ] || exit 1
    GH_TOKEN="$tok" git -c credential.helper= \
        -c 'credential.helper=!gh auth git-credential' \
        push
)
```

Git push 实际使用的认证账号由 transport 和 Git push 凭据配置决定，不得仅根据 `gh` active account 推断。上述 token 注入方式仅适用于对应的 HTTPS / `gh` 凭据路径；其他 transport 不应照搬。

如果当前 `gh` 不支持按 login 获取对应凭据，只有默认凭据已明确属于目标 GitHub 账号时才继续；否则停止对应的 GitHub 外部写入，不自行切换或重配认证。

无法确定正确的 GitHub 账号或 Git push 凭据时，不执行对应的外部写入。读权限、已有认证或能够 clone 仓库，都不构成外部写入授权。

某组凭据认证失败时，只停止依赖该凭据的外部写入；先根据原始错误区分凭据不可用、权限不足和其他故障，本地工作照常继续。认证失败本身不授权修复或绕过认证。

除非用户明确要求修复认证，不运行 `gh auth login`、`gh auth logout`、`gh auth setup-git`，不切换账号或认证机制，也不修改持久 credential helper 或 GitHub CLI 认证配置。

### Skill 冲突与反馈

Skill 指令与现场证据冲突时，以现场证据为准，只偏离冲突部分并继续安全可行的工作；在收尾说明偏离及证据，不顺手修改已安装的 Skill。

问题源于 Skill 本身、且可能在其他任务中复现时，应作为 Skill 缺陷反馈给其权威来源仓库；一次性环境故障和项目自身缺陷不属于 Skill 反馈。优先通过 Skill 管理器的来源元数据确认权威来源仓库，不凭名称或相似仓库猜测。

反馈前确认目标 GitHub 账号和仓库权限。该账号对权威来源仓库具有 `push`、`maintain` 或 `admin` 权限且仓库启用了 Issues 时，视为本指引已预授权直接反馈，无需再次询问。提交前整理并脱敏复现根因所需的最小证据，搜索开放和已关闭的同根因 Issue；已有 Issue 时补充评论，否则创建新 Issue。

无法安全提交反馈时，不阻塞当前任务；继续完成可行工作，并在收尾交接 Skill、可确认的权威来源仓库、预期与实际、最小证据、临时绕法和影响。若提交位置和 Issue 格式已经明确，同时提供可直接提交的草稿。

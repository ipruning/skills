# README

## For Human

你的责任是带 AI 搞清楚：它正在编辑的文件最终给谁看？这个消费者能看到哪些上下文？明确告诉 AI 什么时候写 `README.md`，什么时候写 `AGENTS.md`，什么时候更新 `SKILL.md` 的 YAML `description`。

你的责任是用 System Prompt 让 AI 更好的循环，并在正确的时候与你协作，并尽量少打扰你。

* 比如 AI 在内循环时候，你肯定不喜欢 AI 经常打扰你，你又想 AI 的交付物好。于是，你要教会 AI，交付物放在哪里。你也要教会 AI 怎么更好的用好搜索。
* 在中循环，你要教会 AI 怎么打扰你，无论是通过语音还是通知来喊你鉴权。
* 在大循环，你要教会 AI 怎么写出靠谱的文档，而不是 Slop。

你可以考虑对 AI 的指令用无主语祈使句或隐含第二人称。

你要关注 AI 写下的文档是否在自创术语，或者术语的上位词下位词飞的到处都是。

## 给 AI 的修改规则

先判断要解决的问题，再决定改哪个文件：

* 改项目背景、读者说明、文件边界和长期共识时，写 `README.md`。
* 改 AI 在这个目录或项目中必须遵守的工作规则时，写 `AGENTS.md`。
* 改 Skill 的触发条件、适用范围或排除范围时，更新 `SKILL.md` 的 YAML `description`；不要把这些内容只写在正文里。
* 如果规则只适用于某一种任务或工具用法，优先做成 Skill，按需加载，不要继续堆进常驻文件。

编辑前先读完适用范围内的 `AGENTS.md` 和相关文件。默认只改结构和措辞，不改变已有规则的意思；要删规则或改变边界，先请用户确认。

编辑后检查三件事：规则是否放在正确的文件里，交叉引用和 scope 是否仍然成立，`README.md` 与 `AGENTS.md` 是否同步。发现术语不一致、上下位关系混乱或文档像套话时，直接改成读者能执行的说法。

## 修改纪律

* 默认**只动结构和措辞，不动语义**；删减规则内容需用户逐条确认。
* 新增规则先过准入检验：它是**非显然的 invariant**（边界、身份、证据标准），还是 **how-to**（工具用法、操作步骤）？invariant 才有资格常驻本文件；how-to 优先做成 Skill 按需加载。每条常驻指令都应能说明自己修复了什么真实失败。
* 每次结构调整后核查：交叉引用（「除『Skill 冲突与反馈』一节另有规定外」）、scope 句与子节内容的对应、产物列表与子节顺序的一致。
* 本 README 与 AGENTS.md 同步维护：形成新共识、关闭待定项时更新本文件。

## 变更记录

* 2026-08：**保留「授权边界」「执行过程」「文件与路径发现」现状，压缩到此为止。** 优化目标是信号纯度而非行数最小化；三层循环的自洽是功能性资产（全文只有「产物的消费者是谁」一个判断逻辑）。后续增删的触发器是观察到的事实——模型违反某条边界则加改，某条规则长期无关且可疑则删——不做无证据的进一步浓缩。
* 2026-08：**删除 GNU Parallel 段、压缩 fd/find 选型细节。** 属 how-to 而非 invariant，场景极窄且「实测支持时」难以操作化。保留最小搜索根纪律、「目录名不证明项目归属」与 `--hidden --no-ignore`（影响盘点完整性的正确性陷阱）。若未来实测发现模型乱用 `find` 或滥开并行，凭失败证据恢复相应细则。
* 2026-08：**Amp 的临时兼容 TODO 保持自然语言，不采用固定字段协议。** 真实历史样本表明，固定 `trigger` / `action` 会把事实条件藏进 action，也会被 formatter 折行破坏；六字段卡片又会复写邻近代码和常规验证。消费单元是 TODO、邻近注释与代码。只要求补充 AI 无法从现场可靠推知的信息，并规定普通任务自然遇见相关 TODO 时查验或提醒，但不主动全仓巡检。
* 2026-08：**「临时代码与上下文接力」统一到 amp / claude / codex 三个宿主文件。** claude 与 codex 移除固定 `TODO(cleanup): trigger/action` 标记协议及配套 rg 正则，与 Amp 同步为自然语言目标表达，并补充 canonical Issue URL 路由、「Issue 状态只触发复查」、关闭原因与可点击下一跳。理由同上条；跨宿主共识是按没有本次对话上下文的最终消费者产出，让信息每次转手尽量少损失原始意图。公司同事 AI 侧的同一边界由 jihuanshe/skills#219 引入的 `preserving-intent` Skill 承载（该 Skill 在 jihuanshe/skills#245 由 `preserving-context-continuity` 改名）。随统一删除了旧 amp 的「矛盾影响当前决策时先询问用户」分支：授权边界的重新确认规则已兜底，「与当前任务相称的查验」给出统一处置；「超出范围或无法安全判断时保留并在收尾说明」的报告义务三处保留。
* 2026-08：**Codex 的普通代码注释只保留当前非显然理由。** 普通注释不记录中间尝试、撤回实现、对话纠偏的叙事或从未进入仓库基线的状态。临时兼容、迁移和灰度仍记录当前偏离与可验证的清理条件，因为这些信息决定后续维护动作；完整实现过程不进入注释。
* 2026-08：**brrr payload 改用 `jq -n --arg` 构造。** 单引号 JSON 字面量加裸替换指引，在值含英文单引号时提前闭合 shell 引号形成注入面，值含 `"` 或换行时产出非法 JSON；`jq --arg` 从机制上消除两类破坏。`curl -K -` 与 `header = "..."` 语法经本地抓包复验仍成立。
* 2026-08：**Mock 边界统一为 amp 值（用户裁决）。** 三个宿主文件统一为 Mock 可隔离「当前测试范围之外的协作者或外部边界」；claude/codex 原「只放行不可控外部边界、其余换真实场景」放宽至该值。
* 2026-08：**Skill 缺陷反馈的 Issue 创建统一为 amp 的权限门自主模式（用户裁决）。** claude/codex 与 amp 对齐——匹配 login 对来源仓库拥有 push、maintain 或 admin 权限且仓库启用 Issues 即视为已获授权，完成脱敏与同根因去重后直接创建，无需用户逐次要求；三个宿主的授权边界节相应加入交叉引用例外。
* 2026-08：**阻塞通知级别有意分叉，不同步（用户裁决）。** amp 一律 `time-sensitive`；claude/codex 保留延误造成不可逆后果或错过当天窗口时升级 `critical` 的分支。
* 2026-08：**GitHub 认证失败采用停止扩散边界并统一到三个宿主。** 单账号使用默认凭据；多账号仅在当前 `gh` 明确支持 `auth token --user` 时按 login 注入 token。认证失败后先区分凭据、权限与非认证故障；凭据不可用时停止相关外部写入，不切换账号、上传 API 或认证机制。除非用户明确要求配置或修复认证，不运行 `gh auth login/logout/setup-git`，不修改持久 credential helper 或认证文件。该规则源于旧版 `gh` 环境中一次能力不兼容被过度恢复放大的真实失败，并同步适用于 amp / claude / codex。
* 2026-08：**压缩「咨询神谕」但保留委托边界（用户裁决）。** 将触发时机和八项委托清单合并为四类必要信息，保留单一问题、现场路径与验证入口、Thread ID + `read_thread`、转述不作权威和只读咨询。神谕指出文件不自动产生新的授权；实际修改按当前任务已有授权执行，不因它点名文件而重复询问。
